# Task 1 — Deploy & Harden the Workload

## Overview

This task deploys and hardens the `ledger-api` workload in a local Kubernetes cluster.

The original application contained several security weaknesses including plaintext secrets, root container execution, and insufficient workload isolation.

The hardened deployment applies defence-in-depth controls across workload configuration, identity, secrets management, admission control, and runtime security.

## Architecture

Namespace: `payments`

Workloads:

- `ledger-api` — primary application
- `reporting` — neighbouring service

Kubernetes resources include:

- Deployments
- Services
- ConfigMaps
- Ingress
- ServiceAccounts
- RBAC
- Sealed Secrets
- Kyverno admission policies

## Container Security

The `ledger-api` workload uses a restrictive Kubernetes `securityContext`.

Controls include:

- Runs as a non-root user
- `runAsNonRoot: true`
- Read-only root filesystem
- Linux capabilities dropped
- `allowPrivilegeEscalation: false`
- `seccompProfile: RuntimeDefault`

The application image also uses a dedicated non-root user rather than running as root.

These controls reduce the impact of container compromise and restrict privilege escalation.

## Resource Management

CPU and memory requests/limits are configured to provide predictable scheduling and prevent uncontrolled resource consumption.

Liveness and readiness probes are configured to detect unhealthy application instances and prevent traffic from being routed to pods that are not ready.

## Service Accounts and RBAC

The application does not rely on Kubernetes' default ServiceAccount.

Dedicated ServiceAccounts are used for workloads including:

- `ledger-api`
- `reporting`

RBAC permissions follow least-privilege principles and are scoped only to resources required by the workloads.

This limits the Kubernetes API permissions available to a compromised application.

## Secrets Management

Plaintext application secrets were removed from the Kubernetes manifests.

Bitnami Sealed Secrets is used to safely store encrypted secret material in Git.

A `SealedSecret` can be committed to the repository while the corresponding plaintext Kubernetes Secret can only be generated by the Sealed Secrets controller possessing the private key.

This prevents credentials such as database passwords and API keys from being stored directly in source control.

## Admission Control with Kyverno

Kyverno is used as the Kubernetes admission-policy engine.

Security policies enforce workload requirements including:

### Non-root execution

Containers that do not explicitly run as non-root are rejected.

### Prohibit `:latest`

Container images using the mutable `latest` tag are rejected.

Pinned/versioned image tags are required for predictable and auditable deployments.

### Image trust

Admission controls are used to enforce trusted/signed container images as part of the software supply-chain security model.

These controls move security requirements from developer convention into enforceable cluster policy.

## Security Validation

The security controls were tested by attempting to deploy workloads that violate admission requirements.

Kyverno successfully rejected non-compliant workloads, demonstrating that the controls are enforced by the Kubernetes admission layer rather than relying solely on documentation.

## Security Design

The hardened workload uses multiple independent security layers:

1. **Container hardening** limits privileges inside the pod.
2. **Dedicated ServiceAccounts and RBAC** restrict Kubernetes API access.
3. **Sealed Secrets** protect sensitive configuration stored in Git.
4. **Resource limits and probes** improve workload resilience.
5. **Kyverno** prevents insecure workloads from entering the cluster.
6. **Immutable/versioned images** improve deployment integrity and traceability.

This defence-in-depth approach reduces both the likelihood and potential impact of workload compromise.
